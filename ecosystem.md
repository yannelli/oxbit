# Feature gaps: ecosystem track

Created: 2026-10-02. Last updated: 2026-10-02.

Items 11, 12, and 13 from the [feature gaps index](README.md). Order: 11, 12, 13.

## 11. Extension sandbox and registry

**Current state.** Trusted JavaScript shares host privileges, and manifest
capabilities do not sandbox code (`docs/sdk.md`). Extensions load through
dynamic `import()` in `packages/core/src/index.ts` and
`apps/runtime/src/extensions.ts`. There is no public marketplace.

**Target.** A sandboxed extension tier for untrusted code, a signed registry
with search and one-click install, update checks, and a publishing CLI.

**Design.** Two tiers. Trusted extensions keep today's model. Sandboxed
extensions run in a dedicated Web Worker in the browser and a Node
`worker_threads` worker in the runtime, behind a message-passing shim that
exposes only the SDK services the manifest declares. Declared capabilities
become enforced.

- The SDK shim serializes `ExtensionContext` calls over `postMessage`. UI
  contributions render through declarative descriptors. Custom React components
  stay a trusted-tier feature.
- Registry: a static index served over HTTPS with Sigstore-signed bundles.
  The runtime checks each signature before install. The Extensions view gains
  search, install, update, and ratings.
- Publishing: `oxbit ext publish` in `cli.ts`.

**Steps.**

1. Worker host and SDK shim, with the Bundle Inspector example ported to the
   sandboxed tier
2. Capability enforcement, plus tests that a sandboxed extension cannot reach
   the filesystem without the declared capability
3. Registry index format and signature checking
4. Extensions view search and install
5. Publishing CLI

**Checks.** Unit tests for the shim. A Playwright scenario that installs the
example from a local registry and runs its command.

## 12. VS Code grammar and theme compatibility

**Current state.** Themes use semantic CSS tokens generated by
`packages/themes/scripts/generate.mjs`. Syntax uses Lezer.

**Target.** Load VS Code color themes and TextMate grammars from `.vsix` files or
the registry. This covers the long tail of languages and themes without native
ports.

**Design.**

- Themes: a converter from `tokenColors` and `colors` to the Oxbit token set,
  run at import time and cached. Unmapped keys fall back to the nearest theme
  token and appear in `pnpm themes:coverage` output.
- Grammars: `vscode-textmate` with `vscode-oniguruma` in the tree-sitter worker
  from item 10, registered as a `language` contribution. Tree-sitter wins when
  both exist.
- Import: the Extensions view accepts `.vsix`, extracts `contributes.themes`,
  `contributes.grammars`, and `contributes.languages`, and ignores JavaScript.

**Steps.**

1. Theme converter and import
2. TextMate worker and grammar registration
3. `.vsix` import in the Extensions view

**Checks.** Theme browser tests in `tests/browser/themes.config.ts` gain three
imported VS Code themes. Grammar tests assert scopes on fixture files.

## 13. Tool windows

**Current state.** None of these exist. The panel and activity view contribution
kinds, the task supervisor, and the terminal addon cover the plumbing.

**Target.** Database explorer with a query console, an HTTP client driven by
`.http` files, a Docker containers and images view, and a CPU profiler view for
Node and Python.

**Design.** Each ships as a separate first-party extension so it can be disabled.
Each is a candidate to move to the registry from item 11 later.

- Database: `packages/features/database`. Connections stored in runtime-local
  credentials. Drivers for PostgreSQL, MySQL, and SQLite run in the runtime.
  A schema tree activity view, a query console `documentView` with a results
  grid, and `.sql` language support.
- HTTP client: `.http` and `.rest` language definition, a CodeLens "Send
  request" action from item 6, a response `documentView`, environment files,
  and variables.
- Docker: reads the Docker socket through the runtime. Containers, images,
  volumes, compose services, logs streamed as a terminal, attach as a terminal.
- Profiler: Node `--cpu-prof` and Python `cProfile` runs through the task
  supervisor, a flame graph `documentView`, and open-in-editor from a frame.

**Steps.**

1. HTTP client, the smallest item, depends only on item 6
2. Docker view
3. Database explorer with SQLite first, then PostgreSQL and MySQL
4. Profiler

**Checks.** Runtime unit tests with testcontainers for database and Docker.
Playwright scenario for the HTTP client against a local stub.
